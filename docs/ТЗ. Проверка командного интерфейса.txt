ТЗ. ГЕНЕРАТОР СЦЕНАРИЕВ ПРОВЕРКИ КОМАНДНОГО ИНТЕРФЕЙСА
======================================================

Документ описывает отдельный генератор, который строит сценарии Vanessa Automation для
проверки доступности элементов системы пользователю: какие разделы, команды и формы
он видит в интерфейсе и может открыть.

Существующий генератор UI-сценариев в обработке «АвтоТест1С» решает смежную задачу —
проверяет, что объекты конфигурации открываются. Предлагаемый генератор дополняет его:
он проверяет не объекты, а путь пользователя к ним.

---

1. Зачем это нужно
------------------

Три типичных дефекта, которые не ловятся ничем другим:

  * после доработки команда пропала из панели функций — объект остался, открыть его из меню нельзя;
  * роль изменилась, и пользователь потерял раздел, с которым работал (или, наоборот, увидел лишнее);
  * объект есть, права есть, но команда скрыта настройкой командного интерфейса — пользователь
  до него не доходит.

Все три относятся к доступности, а не к работоспособности форм.

2. Ключевое ограничение: метаданных недостаточно
------------------------------------------------

Установлено прогонами на демо-базе «Розница 2.3» (сентябрь 2026):

| Факт | Следствие |
|---|---|
| Видимость команды в панели функций задаётся настройкой командного интерфейса подсистемы и через Метаданные не читается | По составу подсистемы нельзя узнать, увидит ли пользователь команду. В прогоне 21.09 это дало 38 ложных падений из 47 |
| Право «Просмотр» на подсистему читается (ПравоДоступа("Просмотр", Подсистема, ПользовательИБ)) | Видимость раздела определить можно, видимость команды внутри раздела — нет |
| Подпись команды не совпадает ни с синонимом объекта, ни с заголовком открывшегося окна: «Отражение результатов пересчетов» → окно «Ордера на отражение результатов пересчетов товаров» | Сценарий нельзя построить по имени объекта — нужна фактическая подпись команды |
| Команда открывает не обязательно основную форму списка: у документов ЕГАИС это ФормаСпискаДокументов | Проверять открытие по метаданным основной формы нельзя |

**Вывод: генератор должен строиться не на метаданных, а на фактическом слепке интерфейса,
снятом под конкретным пользователем.**

3. Концепция: два шага
----------------------

        ┌──────────────────┐        ┌──────────────┐        ┌──────────────────┐
        │ 1. Снятие слепка │   →    │ слепок.json  │   →    │ 2. Генерация     │
        │ под пользователем│        │ (разделы,    │        │ .feature-файлов  │
        │                  │        │  команды,    │        │                  │
        └──────────────────┘        │  ссылки)     │        └──────────────────┘
                                    └──────────────┘

Слепок снимается один раз на пользователя (роль) и хранится в репозитории рядом со сценариями.
Он же служит эталоном для регресса: если после доработки команда исчезла, это видно
сравнением слепков ещё до прогона тестов.

Как снимать слепок
~~~~~~~~~~~~~~~~~~

Панель разделов и панель функций недоступны из встроенного языка обычным способом,
но доступны через интерфейс тестирования 1С (ТестируемоеПриложение) — тот же механизм,
которым пользуется Vanessa. Два рабочих варианта:

  * A. Из менеджера тестирования — обработка подключается к TestClient и обходит
  панель разделов, для каждого раздела открывает панель функций и собирает команды.
  Не требует внешних инструментов, встраивается в «АвтоТест1С».
  * B. Через MCP-сервер Vanessa — инструмент manage_command_interface с действиями
  get_section_panel, get_function_panel, get_all. Возвращает разделы, команды
  и навигационные ссылки команд. Быстрее в реализации, но требует запущенной VA.

Рекомендуется A как основной режим и B как вспомогательный (для разовых сборов и отладки).

4. Функциональные требования
----------------------------

4.1. Снятие слепка
~~~~~~~~~~~~~~~~~~

| № | Требование |
|---|---|
| КИ-01 | Слепок снимается под указанным пользователем информационной базы (логин/пароль или профиль TestClient) |
| КИ-02 | Собирается панель разделов: имя раздела в том виде, в каком он подписан в интерфейсе |
| КИ-03 | Для каждого раздела собирается панель функций: подпись команды, навигационная ссылка, группа (если команды сгруппированы) |
| КИ-04 | Для каждой команды по навигационной ссылке определяется объект метаданных, на который она ведёт |
| КИ-05 | Собирается состав начальной страницы (формы рабочего стола) — это тоже часть доступности |
| КИ-06 | Слепок сохраняется в JSON с указанием пользователя, конфигурации, её версии и даты снятия |
| КИ-07 | Снятие слепка не изменяет данные базы |

4.2. Генерация сценариев
~~~~~~~~~~~~~~~~~~~~~~~~

| № | Требование |
|---|---|
| КИ-10 | На каждый раздел слепка создаётся файл .feature («Командный интерфейс. Закупки.feature») |
| КИ-11 | Контекст фичи подключает TestClient под пользователем, для которого снят слепок |
| КИ-12 | На каждый раздел — сценарий «раздел доступен»: раздел присутствует в панели разделов |
| КИ-13 | На каждую команду — сценарий «команда открывается»: выбор команды в разделе, проверка, что окно открылось и не осталось начальной страницей |
| КИ-14 | Для команд с навигационной ссылкой дополнительно проверяется, что открылась форма ожидаемого объекта (ссылка из слепка) |
| КИ-15 | На начальную страницу — сценарий «формы рабочего стола открылись» |
| КИ-16 | Поддерживаются исключения объектов и команд в формате генератора дымовых тестов Vanessa (каталог *.txt, строка Объект[.ТипПроверки], маски) |
| КИ-17 | Каталог выгрузки очищается от файлов прошлой генерации перед записью |
| КИ-18 | Повторная генерация по тому же слепку даёт побайтово тот же результат (идемпотентность) |

4.3. Негативные проверки (доступность «от противного»)
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

| № | Требование |
|---|---|
| КИ-20 | По слепкам двух пользователей строится набор «чего быть не должно»: разделы и команды, доступные первому и недоступные второму |
| КИ-21 | Сценарий проверяет, что раздел/команда отсутствует у пользователя, которому не положен |
| КИ-22 | Негативные наборы генерируются только по явному указанию: их ценность в контроле разграничения прав, и они требуют осмысленных пар ролей |

4.4. Регресс интерфейса
~~~~~~~~~~~~~~~~~~~~~~~

| № | Требование |
|---|---|
| КИ-30 | Сравнение двух слепков (эталон/текущий) с отчётом: появилось, исчезло, переименовано |
| КИ-31 | Исчезновение команды или раздела — ошибка; появление — предупреждение |
| КИ-32 | Отчёт сравнения выгружается в JSON (для CI) и в удобочитаемый вид (для разбора) |

----------------

      "Дата": "2026-09-21T12:19:00",
      "Разделы": [
        {
          "Имя": "Закупки",
          "Команды": [

6. Примеры генерируемых сценариев
---------------------------------

    #language: ru
    @tree
    @КомандныйИнтерфейс
    Функциональность: Командный интерфейс. Закупки
    
    Контекст:
    	И я подключаю TestClient "БушуевЭР (Менеджер)" логин "БушуевЭР (Менеджер)" пароль "$Пароль$"
    	И я закрываю все окна клиентского приложения
    
    @Раздел @Закупки
    Сценарий: Раздел «Закупки» доступен пользователю
    	Тогда в командном интерфейсе доступен раздел "Закупки"
    
    @Команда @Закупки @Справочник_Контрагенты
    Сценарий: Закупки → Поставщики открывается
    	И В командном интерфейсе я выбираю "Закупки" "Поставщики"
    	И Пауза 2
    	Тогда открылась форма с именем 'Справочник.Контрагенты.Форма.ФормаСписка'
    	И я закрываю все окна клиентского приложения

Негативный сценарий:

    @Негативный @Администрирование
    Сценарий: Раздел «Администрирование» пользователю недоступен
    	Тогда в командном интерфейсе раздел "Администрирование" отсутствует

Шаги доступен раздел / раздел отсутствует в стандартной поставке Vanessa отсутствуют —
их нужно реализовать в расширении шагов (VAExtension) поверх интерфейса тестирования.
До их появления допустим обходной вариант: выбор раздела штатным шагом и проверка,
что шаг не завершился ошибкой.

7. Интеграция с «АвтоТест1С»
----------------------------

Генератор реализуется как отдельная область в модуле объекта обработки и отдельная
группа на форме, чтобы существующий генератор UI-сценариев остался независимым:

  * новые команды формы: «Снять слепок интерфейса», «Сгенерировать проверки интерфейса»,
  «Сравнить со слепком»;
  * новые настройки: путь к слепку, каталог эталонных слепков, режим негативных проверок;
  * общие с текущим генератором: каталог сценариев, каталог исключений, пользователь и пароль,
  очистка каталога перед выгрузкой.

8. Нефункциональные требования
------------------------------

| № | Требование |
|---|---|
| НФ-01 | Снятие слепка на конфигурации масштаба «Розница 2.3» — не более 5 минут |
| НФ-02 | Генерация по готовому слепку — не более 30 секунд, без обращения к клиенту тестирования |
| НФ-03 | Работа в пакетном режиме для CI: снятие слепка, сравнение, генерация — параметрами командной строки |
| НФ-04 | Ни один шаг не изменяет данные базы |
| НФ-05 | Все сообщения об ошибках называют объект и раздел, а не только факт ошибки |

9. Ограничения и риски
----------------------

  * Слепок устаревает. После изменения ролей или командного интерфейса его нужно снимать заново;
  иначе сценарии проверяют вчерашний интерфейс. Митигация — КИ-30 (сравнение) в CI.
  * Зависимость от данных. Часть команд появляется в меню по условию (включённая функциональная
  опция, заполненные данные). Слепок фиксирует состояние конкретной базы — эталон нужно снимать
  на эталонной базе.
  * Интерфейс тестирования требует UI-сеанса. Снятие слепка нельзя выполнить полностью headless;
  нужен запущенный клиент тестирования и незаблокированный рабочий стол.
  * Модальные окна. Если при входе пользователя появляется диалог (например, «Изменения 54-ФЗ»),
  сбор должен его закрывать, иначе панель функций недоступна.

10. Критерии приёмки
--------------------

1. Слепок, снятый под пользователем с ограниченными правами, содержит ровно те разделы,
   которые пользователь видит в панели разделов (сверка вручную по скриншоту).
2. Сгенерированный по слепку набор проходит без падений на той же базе и под тем же пользователем.
3. Удаление команды из командного интерфейса подсистемы приводит к падению соответствующего
   сценария и к записи «исчезло» в отчёте сравнения слепков.
4. Негативный набор падает, если пользователю выдали роль, открывающую запрещённый раздел.
5. Повторная генерация по неизменному слепку не меняет содержимое файлов.

УЛУЧШЕНИЯ ТЕКУЩЕГО ГЕНЕРАТОРА UI-СЦЕНАРИЕВ
==========================================

Список составлен по результатам четырёх прогонов на демо-базе (21.09.2026: 104, 333, 575 и 87
сценариев). Приоритет — по соотношению «снятые ложные падения / трудозатраты».

  | Статус на 21.09.2026. Реализованы и проверены прогонами: У-01, У-02, У-03, У-04, У-07.
  | Реализованы все десять улучшений У-01…У-10. Остаётся сам генератор проверок
  | командного интерфейса по требованиям КИ-01…КИ-32 — это отдельная задача.

Высокий приоритет
-----------------

У-01. Проверка «список не пуст» вместо простого открытия. ✅ Реализовано.
Сейчас сценарий подтверждает, что форма открылась. Добавить опциональную проверку, что в списке
есть хотя бы одна строка, — тогда набор начнёт ловить пустые справочники после неудачного обмена
или миграции. Реализуется шагом Тогда в таблице "Список" количество строк "больше" 0,
включается флажком, по умолчанию выключено (на чистой базе списки законно пусты).

У-02. Слепок «что открылось» вместо предположений. ✅ Реализовано.
Однократно прогнать набор в режиме обучения, записать для каждого объекта фактическое имя
открывшейся формы и заголовок окна, сохранить в JSON. Дальше генерировать сценарии по факту,
а не по метаданным. Это закрывает целый класс проблем, на которые мы потратили три итерации:
ФормаСпискаДокументов у ЕГАИС, «Приемка товаров» вместо «Приходные ордера», «Остатки на складах»
вместо «Ведомость по товарам».

У-03. Автоматическое пополнение исключений по результатам прогона. ✅ Реализовано.
Разобрать Allure-результаты и предложить готовые строки исключений для объектов, упавших
со «штатными» отказами («Самостоятельное использование формы не предусмотрено», «только
на основании», «не выбран сегмент»). Сейчас это делается вручную и занимает больше времени,
чем сам прогон.

Средний приоритет
-----------------

У-04. Теги критичности и бизнес-процесса как фильтр прогона. ✅ Реализовано.
Теги уже проставляются (@Критичность2, @Справочник_Номенклатура), но набор всегда гоняется
целиком. Добавить в генератор параметр «минимальная критичность» для выгрузки — быстрый
smoke-набор для каждого коммита и полный набор на ночь.

У-05. Проверка печатных форм и команд «Создать на основании». ✅ Реализовано.
Самые дорогие в поддержке места конфигурации; сейчас не покрыты. Генерируются по метаданным:
МО.Макеты и МО.ВводитсяНаОсновании.

У-06. Разделение набора на «читающий» и «пишущий». ✅ Реализовано.
Сейчас все сценарии только открывают формы. Если добавить запись объекта (У-05 и далее),
такие сценарии нужно вынести в отдельные файлы с тегом @ИзменяетДанные, чтобы их можно было
не гонять на копии рабочей базы.

У-07. Учёт функциональных опций. ✅ Реализовано.
Объект может быть скрыт выключенной функциональной опцией — сценарий по нему упадёт
по той же причине, что и скрытая команда. Опции читаются из метаданных
(МО.ФункциональныеОпции), значение — из константы: можно не генерировать проверки
для объектов с выключенной опцией.

Низкий приоритет
----------------

У-08. Параллельный прогон. ✅ Реализовано. Набор из 575 сценариев идёт около часа. Vanessa умеет работать
с несколькими клиентами тестирования — генератор может раскладывать файлы по группам
для параллельного запуска.

У-09. Отчёт «покрытие интерфейса». ✅ Реализовано. Сколько объектов конфигурации покрыто сценариями,
в разрезе разделов и бизнес-процессов. У обработки уже есть механизм расчёта покрытия
для серверных проверок — переиспользовать его.

У-10. Локализация. ✅ Реализовано. Сейчас шаги генерируются на русском. Для конфигураций с английским
интерфейсом понадобится второй набор шаблонов; Vanessa это поддерживает.

Что делать в первую очередь
---------------------------

У-02 и У-03. Обе бьют в одну точку — в цикл «прогнал → разобрал падения → поправил генератор»,
на который ушла большая часть времени. После них добавление новых видов проверок (У-05)
перестанет быть дорогим.
