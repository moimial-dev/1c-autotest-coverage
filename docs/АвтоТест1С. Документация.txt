АВТОТЕСТ1С — ОБРАБОТКА ТЕСТИРОВАНИЯ 1С С ПОКРЫТИЕМ «ИЗ КОРОБКИ»
===============================================================

Реализация черновика требований v0.1 «Платформа тестирования 1С с покрытием из коробки»
в формате внешней обработки (.epf), работающей на любой конфигурации без настройки
сценариев.

Подключились к базе → нажали «Выполнить прогон» → получили карту объектов, автопокрытие,
покрытие по подсистемам и риск-карту. Ни одной строки сценария писать не нужно.

Состав
------

| Файл | Назначение |
|---|---|
| АвтоТест1С.xml + АвтоТест1С/ | исходники обработки (иерархический формат выгрузки) |
| АвтоТест1С/Ext/ObjectModule.bsl | ядро: карта объектов, генерация данных, проверки, покрытие, риск-карта, отчёты |
| АвтоТест1С/Forms/Форма/Ext/Form/Module.bsl | UI, обход интерфейса на клиенте, пакетный режим для CI |
| ../АвтоТест1С.epf | собранная обработка |

Сборка из исходников:

    "C:\Program Files (x86)\1cv8\8.3.27.2130\bin\1cv8.exe" DESIGNER /F<пустая-база> /LoadExternalDataProcessorOrReportFromFiles "Исходники\АвтоТест1С\АвтоТест1С.xml" "АвтоТест1С.epf" /DisableStartupDialogs /DisableStartupMessages /Out build.log

Как работает прогон
-------------------

1. Карта объектов (FR-01). Обход Метаданные: справочники, документы, регистры всех
   видов, планы видов характеристик и счетов, бизнес-процессы, задачи, отчёты, обработки,
   константы, планы обмена. Для каждого объекта — подсистемы, число реквизитов, табличных
   частей и форм, MD5-подпись структуры.
2. Отображение на бизнес-процессы (FR-19, FR-20). Объект метаданных сопоставляется
   процессу («Продажа и касса», «Отгрузка и склад», «Зарплата и персонал», «Интеграции и
   обмены», …) по словарю правил и критичности 1–3. Именно это позволяет говорить с
   заказчиком на языке процессов, а не имён метаданных.
3. Серверные проверки (FR-05). Для каждого объекта: запрос к таблице, создание объекта,
   ОбработкаЗаполнения, автозаполнение реквизитов, для документов — проведение и контроль
   наличия движений; для отчётов — компоновка макета по схеме СКД; для регистров остатков —
   виртуальная таблица.
4. Генерация тестовых данных (FR-03). Значения подбираются по типу: строки с учётом
   квалификаторов длины, числа по смыслу имени (Количество→1, Сумма/Цена→100, Процент→0),
   даты — текущая, ссылки — реально существующие непомеченные элементы базы (с кешем),
   перечисления — первое значение. Заполняется и первая строка каждой табличной части.
5. Обход интерфейса (FR-02). Клиент создаёт каждую форму конфигурации через
   ПолучитьФорму и ловит исключения модулей форм. Формы записи регистров исключены —
   они дают ложные срабатывания.
6. Покрытие и риск-карта (FR-18, FR-20). Покрытие считается по корневым подсистемам;
   риск ранжируется как критичность × (ошибки × 3 + предупреждения) с вердиктом
   от «Проверено, рисков не найдено» до «Не выпускать без разбора».

Безопасность данных. Все записи выполняются внутри транзакции, которая гарантированно
отменяется (ОтменитьТранзакцию под ТранзакцияАктивна()). База после прогона не изменяется.

Порог ложных срабатываний (открытый риск из требований) снижается классификатором
ошибок: «поле не заполнено» → «Предупреждение: неполные тестовые данные», нарушение прав →
«Предупреждение: ограничение прав доступа», всё остальное → «Ошибка: дефект».

Анализ влияния изменений (FR-08, FR-12)
---------------------------------------

1. До доработки — «Сохранить снимок конфигурации» (JSON с MD5-подписями структуры каждого
   объекта).
2. После доработки — включить «Только затронутые изменением» и выполнить прогон.
3. Обработка сравнивает подписи, находит изменённые/добавленные/удалённые объекты, добавляет
   зависимые (объекты того же бизнес-процесса) и прогоняет только их.

Генератор UI-сценариев для Vanessa Automation (FR-02, FR-06)
------------------------------------------------------------

Кнопка «Сгенерировать сценарии Vanessa» строит по карте объектов готовый набор
.feature-файлов — те же проверки интерфейса, что обработка делает своим обходом форм,
но в виде обычных сценариев, которые запускаются в Vanessa Automation и попадают
в отчёт Allure наравне с ручными тестами.

Сценариев писать по-прежнему не нужно: набор строится из метаданных при каждой генерации,
поэтому новые объекты появляются в наборе сами, а удалённые исчезают.

Что генерируется на объект:

| Проверка | Сценарий | Для каких объектов |
|---|---|---|
| Список открывается | открыть e1cib/list/<объект>, дождаться основной формы списка | справочники, документы, ПВХ, планы счетов и обмена, бизнес-процессы, задачи, регистры |
| Форма создания открывается | открыть e1cib/data/<объект>, дождаться основной формы объекта | всё, кроме регистров, отчётов, обработок и подчинённых объектов |
| Форма открывается | открыть e1cib/data/<объект> | отчёты, обработки (обработки — по флажку, они могут что-то делать при открытии) |

Открытие проверяется по имени формы (Тогда открылась форма с именем '…'), а не по
заголовку окна. Заголовок задаётся внутри формы и зависит от данных: список приходных
ордеров называется «Приемка товаров», отчёт «Ведомость по товарам на складах» открывается
как «Остатки на складах» — сверка заголовка давала ложные падения. Имя формы берётся
из метаданных (основная форма списка/объекта); если основная форма не задана,
генератор возвращается к проверке заголовка.

Форма создания не проверяется у подчинённых объектов: платформе нужен владелец,
и по ссылке e1cib/data/… вместо формы остаётся начальная страница.
| Открывается из раздела | И В командном интерфейсе я выбираю "Закупки" "Поставщики" | справочники и документы, входящие в подсистему командного интерфейса; по умолчанию выключено |

Последняя проверка отличается от остальных тем, что идёт тем же путём, что и пользователь:
панель разделов → панель функций → форма. Навигационная ссылка открывает форму в обход меню,
поэтому пропавшая или переименованная команда раздела остаётся незамеченной — этот сценарий
её ловит. Раздел берётся из корневой подсистемы объекта, подпись команды — из представления
списка (у справочника «Контрагенты» в разделе «Закупки» это «Поставщики»).

Сценарий проверяет только одно: команда есть в меню и нажимается. Что именно откроется,
заранее неизвестно — команда ведёт не обязательно на основную форму списка (у документов
ЕГАИС это «ФормаСпискаДокументов»), а заголовок окна не совпадает ни с синонимом объекта,
ни с подписью команды («Отражение результатов пересчетов» → «Ордера на отражение
результатов пересчетов товаров»). Открытие форм проверяют сценарии по навигационным ссылкам.

Видимость команд в панели функций настраивается в конфигураторе и через метаданные
не читается, поэтому по составу подсистемы нельзя понять, увидит ли команду пользователь.
Справочники и документы попадают в панель почти всегда, а отчёты, обработки и планы видов
характеристик там чаще скрыты — они из этой проверки исключены совсем. Если команда скрыта
и для справочника, сценарий упадёт с понятным «Команда меню … не найдена в панели функций»
и списком того, что в панели есть. Такие объекты выносятся в исключения по типу проверки:

    ВариантыРаспределенияТоваров.КомандныйИнтерфейс
    ОрдерНаОтражениеИзлишковТоваров.КомандныйИнтерфейс

Проверка остальных видов при этом сохраняется. Если разбираться с каждым объектом не нужно,
флажок «Команды разделов» просто не включают — по умолчанию он выключен.

У полей «Каталог сценариев Vanessa», «Каталог отчётов» и «Файл снимка конфигурации»
есть кнопка выбора: она открывает системный диалог, так что путь не обязательно
набирать руками.

Куда обработка кладёт файлы
~~~~~~~~~~~~~~~~~~~~~~~~~~~

Все пути по умолчанию ведут в один рабочий каталог C:\1C-auto\АвтоТест1С:

| Поле | Значение по умолчанию |
| --- | --- |
| Каталог отчётов | C:\1C-auto\АвтоТест1С |
| Каталог сценариев Vanessa | …\сценарии-vanessa |
| Каталог исключений | …\исключения |
| Каталог результатов прогона | …\allure-results |
| Файл снимка конфигурации | …\снимок-конфигурации.json |
| Файл слепка форм | …\слепок-форм.txt |

Каталога может не быть — обработка создаёт его сама при открытии формы и перед
каждой записью. Раньше пути вели во временный каталог: он у каждого пользователя
свой, чистится системой и найти в нём набор сценариев трудно.

Файлы пишет клиент, а не сервер. Сервер только считает содержимое —
тексты фич, JSON снимка, отчёты, заготовки исключений, — а записывает их
клиентское приложение. В файловой базе разницы не видно, но в клиент-серверной
каталог C:\1C-auto есть на машине пользователя, а не на сервере приложений,
и записанный сервером набор пользователь у себя просто не нашёл бы.

Вызов генератора из кода (сценария, пакетного режима) по-прежнему сохраняет
файлы сам: за это отвечает настройка ЗаписыватьФайлы, по умолчанию включённая.
Форма выставляет её в Ложь и пишет набор сама.

Настройки задаются в группе «Сценарии Vanessa Automation» на форме: каталог выгрузки,
состав проверок, профиль TestClient (если прогон идёт под конкретным пользователем),
лимит сценариев и группировка — по бизнес-процессам (файл «UI. Продажа и касса.feature»)
или по видам объектов.

Исключения объектов
~~~~~~~~~~~~~~~~~~~

Часть объектов конфигурации открывать напрямую не положено: присоединённые файлы
показываются только из карточки-владельца, отчёт может требовать запуска из своей формы,
служебные регистры БСП формы списка не имеют. Такие объекты исключаются файлами —
формат тот же, что у генератора дымовых тестов Vanessa.

В поле «Каталог исключений» указывается каталог с *.txt, имя файла начинается с вида
объекта: Справочники.txt, Документы.txt, РегистрыСведений.txt, Отчеты.txt и так далее.
Кнопка «Создать файлы исключений» раскладывает заготовки по всем видам с пояснениями
в комментариях; существующие файлы не трогаются.

Одна строка — один объект, пустые строки и строки с // пропускаются:

    // Формат: ИмяОбъекта[.ТипПроверки]
    ПрисоединенныеФайлы*            // маска: все присоединённые файлы
    РассылкиОтчетов.Список          // только форма списка, остальные проверки останутся
    НастройкиПочты.Создание         // только форма создания
    УслугиСервиса                   // объект целиком

Тип проверки — Список, Создание, Форма или КомандныйИнтерфейс; без него объект
исключается целиком. Сколько проверок отсеяно, видно в логе генерации.

Набор под конкретного пользователя
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

Поле «Пользователь (права)» выбирается из списка пользователей информационной базы.
Когда пользователь выбран, в набор попадают только объекты, доступные ему по ролям, —
то есть ровно то, что этот пользователь видит сам. Так проверка не превращается
в проверку прав: сценарий по недоступному объекту падал бы на отказе в доступе,
а не на дефекте интерфейса. Сколько объектов отсеяно, видно в логе прогона:

    Сценарии Vanessa: объектов — 37, сценариев — 65, файлов — 9.
    Отбор по правам пользователя «bot_mag1c»: пропущено недоступных объектов — 41.

Пустое значение («все объекты конфигурации») отключает отбор.

Одних прав мало: объект может быть доступен по ролям, но не входить ни в один раздел,
который пользователь видит в панели разделов, — в интерфейсе такой объект ему недостижим.
За это отвечает флажок «Только видимые разделы»: с ним в набор попадает лишь то,
до чего пользователь может дойти по меню. Видимость раздела определяется правом
«Просмотр» на подсистему.

Флажок «Файлы по разделам меню» называет файлы так же, как разделы в интерфейсе:
UI. Закупки.feature, UI. Склад.feature, UI. Финансы.feature. Объекты вне разделов
(регистры, служебные справочники) собираются в UI. Вне разделов.feature. Если флажок снять,
работает прежняя группировка — по бизнес-процессам, а при снятых обоих — по видам объектов.

Пример для пользователя с ролью менеджера: из 972 объектов конфигурации по правам осталось 787,
после отбора по видимым разделам — 145, и набор лёг ровно в четыре файла по его меню:
«Закупки», «НСИ», «Склад», «Финансы».

Перед выгрузкой каталог очищается от файлов прошлой генерации (UI. *.feature): иначе после
смены пользователя или группировки рядом остаются старые файлы и кажется, будто в набор
попали лишние разделы.

Доступность считается через ПравоДоступа("Просмотр" | "Чтение", <объект>, <пользователь>).
Важно: третьим параметром передаётся объект ПользовательИнформационнойБазы, а не его
уникальный идентификатор — с идентификатором платформа отвечает по текущему сеансу
и возвращает «право есть» даже для несуществующего пользователя.

Набор под пользователя и выполняется под ним: в контекст каждой фичи попадает шаг

    	И я подключаю TestClient "БушуевЭР (Менеджер)" логин "БушуевЭР (Менеджер)" пароль "1"

Логин — имя для входа выбранного пользователя ровно в том виде, в каком оно записано
в базе. Его нельзя «подчищать»: имя входа само может содержать скобки, как
«БушуевЭР (Менеджер)» в демо-базе Розницы, и обрезанный вариант в базе просто не найдётся.
Поэтому и список на форме показывает имена входа как есть, без добавления полного имени.

Пароль берётся из поля «Пароль» рядом со списком (вводится в скрытом виде, в сценарий
попадает как есть). Именем клиента тестирования служит поле «Профиль TestClient»,
а если оно пустое — имя пользователя: Vanessa создаст профиль с такими параметрами
на основе текущего подключения.

Без выбранного пользователя контекст прежний — «Дано Я запускаю сценарий открытия TestClient
или подключаю уже существующий», то есть прогон идёт под тем, кто запустил менеджер тестирования.

Каждый сценарий закрывает за собой окна и ничего не записывает в базу. Два места,
где сценарии намеренно снисходительны, — оба про штатное поведение конфигурации,
а не про дефекты:

  * объект, который нельзя вводить вручную («только на основании…»), отвечает
  предупреждением вместо формы — это засчитывается как пройденная проверка;
  * форма, которая заполняет себя при открытии и спрашивает про сохранение,
  закрывается ответом на диалог.

Теги сценария — @UI, вид проверки, критичность объекта и его полное имя
(@Справочник_Номенклатура). По последнему отбирается прогон после точечной доработки.

Программно то же самое:

    Настройки = Обработка.НастройкиГенерацииСценариев();
    Настройки.КаталогСценариев = "C:\features";
    Результат = Обработка.СгенерироватьСценарииVanessa(Настройки);

Ожидания вместо пауз
~~~~~~~~~~~~~~~~~~~~

Сценарии не отсчитывают фиксированные секунды, а ждут события. Форма списка
открывается за доли секунды, и Пауза 2 на каждом из сотен сценариев — это минуты
простоя за прогон.

| Что ждём | Шаг |
| --- | --- |
| Известна форма (список, объект) | И я жду открытия формы с именем "…" в течение 15 секунд |
| Неизвестно, что откроется | И я запоминаю текущее окно как "ОкноДоДействия" + И я жду открытия окна отличного от "$ОкноДоДействия$" в течение 15 секунд |
| Наполнение динамического списка | И я жду, что в таблице "Список" количество строк будет "больше" 0 в течение 15 секунд |

Ожидание «любого другого окна» нужно там, где результат действия заранее неизвестен:
форма создания может не открыться вовсе — конфигурация ответит «вводится только
на основании», и это штатный отказ, а не дефект. Ждать конкретную форму в таком месте
значило бы падать на нормальном поведении.

Таймаут задаётся настройкой ТаймаутОжидания (по умолчанию 15 секунд) — это верхняя
граница на худший случай, а не время, которое сценарий проводит в ожидании.
Фиксированная пауза осталась только в ветке Исключение (пустой список — ждать нечего,
а пустым блок оставить нельзя).

Печать и ввод на основании
~~~~~~~~~~~~~~~~~~~~~~~~~~

Два самых дорогих в поддержке места конфигурации, и оба до сих пор не были покрыты.

Откуда берётся команда печати. Из БСП, а не из макетов: синоним макета
(«ПФ MXL Поступление товаров») и подпись команды («М-4 (Приходный ордер)») — разные
вещи, и по макету кнопку на форме не найти. Команды печати живут в модуле менеджера:

    Коллекция = УправлениеПечатью.СоздатьКоллекциюКомандПечати();
    Менеджер  = ОбщегоНазначения.МенеджерОбъектаПоПолномуИмени(МО.ПолноеИмя());
    Менеджер.ДобавитьКомандыПечати(Коллекция);

Предпочитается команда с признаком ОсновнаяПечатнаяФорма или КомандаПоУмолчанию,
иначе берётся первая подходящая. В конфигурациях, где эти признаки не проставлены
(в «Рознице» — ни у одной команды), выбор остаётся эвристикой: у поступления товаров
первой идёт «Акт расхождений», который печатается пустым, когда расхождений нет.
Такие объекты исключают или задают команду вручную.

Что делает сценарий. Ищет объект запросом — при прогоне, а не при генерации:
зашитый идентификатор живёт ровно до первой перезаливки данных. Печатают проведённый
документ (настройка ПечатьТолькоПроведенных): с черновика конфигурация либо откажет,
либо напечатает никому не нужное.

    И я выполняю код встроенного языка на сервере с передачей переменных
    """bsl
    	Запрос = Новый Запрос("ВЫБРАТЬ ПЕРВЫЕ 1 Т.Ссылка КАК Ссылка ИЗ Документ.ОприходованиеТоваров КАК Т
    		ГДЕ Т.Проведен И НЕ Т.ПометкаУдаления УПОРЯДОЧИТЬ ПО Т.Дата УБЫВ");
    	Выборка = Запрос.Выполнить().Выбрать();
    	Если Выборка.Следующий() Тогда
    		Контекст.Вставить("ЕстьЧтоПечатать", "Да");
    		Контекст.Вставить("СсылкаНаОбъект", ПолучитьНавигационнуюСсылку(Выборка.Ссылка));
    	Иначе
    		Контекст.Вставить("ЕстьЧтоПечатать", "Нет");
    	КонецЕсли;
    """
    Если переменная "ЕстьЧтоПечатать" имеет значение "Да" Тогда
    	Дано Я открываю навигационную ссылку "$СсылкаНаОбъект$"
    	И я жду открытия формы с именем "Документ.ОприходованиеТоваров.Форма.ФормаДокумента" в течение 8 секунд
    	И я нажимаю на кнопку с именем 'ПодменюПечать*__АктОбОприходованииТоваров'
    	И я жду открытия формы с именем "ОбщаяФорма.ПечатьДокументов" в течение 30 секунд
    	И я жду, что табличный документ "ПечатнаяФорма1" заполнится данными в течение 30 секунд
    И я закрываю все окна клиентского приложения

Три вещи здесь неочевидны, и каждая стоила отдельного разбора:

  * Кнопка нажимается по имени, а не по подписи. Команды печати лежат в свёрнутом
  подменю, и клик по подписи упирается в «недоступный пользователю элемент управления».
  Имя платформа собирает из идентификатора команды, префикс зависит от того, попала
  команда в «Важное» или в «Обычное» — отсюда маска ПодменюПечать*__<Идентификатор>.
  * Окно печати ждут по имени формы. Заголовок у него тот же, что у документа
  («Оприходование товаров ТСРТ-000001 от …»), поэтому ожидание «окна с другим
  заголовком» висит до самого таймаута. Имя задаётся настройкой ФормаПечатиБСП;
  очистив её, генератор вернётся к ожиданию любого нового окна.
  * Проверяется заполнение, а не открытие. В форме печати есть штатная группа
  «Печатная форма недоступна» — окно открывается и при пустом результате. Ждём данных
  в поле ПечатнаяФорма1 (настройка ЭлементПечатнойФормы): пустая печатная форма
  и есть тот дефект, ради которого проверка пишется.

Печать дороже открытия формы — платформа формирует макет, БСП собирает данные, —
поэтому у её шагов свой таймаут ТаймаутПечати (30 секунд против общих 8).

Ввод на основании устроен так же: основание ищется запросом, открывается по ссылке,
дальше «Создать на основании» → нужный документ.

Обе проверки по умолчанию выключены. Первый прогон на новой базе стоит разобрать:
часть команд печати открывает диалог параметров (в «Рознице» — «Выбор цен номенклатуры»),
и такие объекты уходят в исключения — сценарий диалоги не проходит.

Читающие и пишущие наборы
~~~~~~~~~~~~~~~~~~~~~~~~~

Открытие формы данных не меняет, а вот заполненная на основании форма уже считается
изменённой и при закрытии предлагает запись. Такие сценарии выносятся в отдельные файлы
с суффиксом (изменяет данные) и тегом @ИзменяетДанные — и у файла, и у каждого
сценария. Набор целиком отсекается при запуске:

    vanessa-automation.epf ... /C"...;FilterTags=~@ИзменяетДанные"

Флажок «Пишущие — отдельно» включён по умолчанию; если его снять, всё сложится
в один файл, как раньше.

Параллельный прогон
~~~~~~~~~~~~~~~~~~~

Поле «Потоков» раскладывает набор по подкаталогам поток-1, поток-2, …
Балансировка идёт по числу сценариев, а не файлов: раздел «Склад» один стоит трёх мелких,
и потоки заканчивают примерно вместе. В логе видно раскладку:

    Набор разложен на 3 потока — поток-1: 214, поток-2: 209, поток-3: 205.

Каждый подкаталог запускается своим клиентом тестирования; при значении 1 (по умолчанию)
раскладки нет и файлы лежат в корне каталога сценариев.

Покрытие интерфейса
~~~~~~~~~~~~~~~~~~~

Кнопка «Покрытие интерфейса» пишет рядом с отчётами файл
АвтоТест1С-покрытие-интерфейса.md: сколько объектов конфигурации попало в набор
в разрезе разделов и — главное — почему не попали остальные.

    Покрытие интерфейса: 9 из 29 объектов (31,0 %).
      Закупки: 2 из 2
      Маркетинг: 0 из 2
    
    | Раздел | Объект | Почему не покрыт |
    | Вне разделов | Документ.АктИнвентаризацииСАТУРН | выключена опция «ВестиУчетПестицидов…» |
    | Маркетинг | РегистрНакопления.БонусныеБаллы | нечего проверять при текущих настройках |

Причина у каждого объекта своя: нет прав у пользователя, файл исключений, выключенная
функциональная опция, критичность ниже порога, объекта нет в доступных разделах.
Покрытие считается во время генерации: отдельный пересчёт после смены настроек
дал бы другие цифры, поэтому кнопка работает по последнему сгенерированному набору.

Язык набора

Поле «Язык шагов» (ru / en) переключает и шапку фичи (#language: en,
Feature:, Background:, Scenario:), и сами шаги на английскую библиотеку Vanessa.
Нужно для конфигураций с английским интерфейсом; по умолчанию — русский.

Дополнительные проверки и фильтры
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

Списки не пусты. Флажок добавляет в сценарий списка проверку
Тогда в таблице "Список" количество строк "больше" 0. На чистой базе списки законно пусты,
поэтому по умолчанию выключено; на рабочих данных пустой список — признак неудавшегося
обмена или миграции.

Учитывать функциональные опции. Объект, скрытый выключенной функциональной опцией,
недоступен в интерфейсе так же, как объект без прав. Генератор читает состав опций и значение
из хранилища и такие объекты пропускает. Опции с параметрами (зависящие от организации,
склада) считаются включёнными: их значение зависит от данных. На демо-базе «Розница»
это отсекает 513 объектов метаданных из 1277.

Критичность от. Каждому объекту присвоена критичность 1–3 (по бизнес-процессу).
Фильтр оставляет в наборе только объекты не ниже заданной: быстрый набор для каждого коммита
(критичность 3 — 624 сценария вместо 1344) и полный набор на ночь.

Слепок фактических форм
~~~~~~~~~~~~~~~~~~~~~~~

Метаданные говорят, какая форма списка основная, но открывается не всегда она: команда раздела
у документов ЕГАИС открывает ФормаСпискаДокументов, у планов обмена автоформа называется
ПланОбмена.АвтономнаяРабота.ФормаСписка (без «.Форма.»), а заголовок окна вообще живёт своей
жизнью — «Приемка товаров» вместо «Приходные ордера на товары».

Поэтому имя формы можно взять из факта, а не из метаданных:

1. Включить флажок «Обучающий набор» и сгенерировать набор. Его сценарии открывают объект,
   запоминают имя открывшейся формы и дописывают строку в файл слепка.
2. Прогнать этот набор один раз в Vanessa.
3. Снять флажок и генерировать обычный набор — имена форм берутся из слепка,
   метаданные остаются запасным вариантом.

Файл слепка — обычный текст, строки вида
ПолноеИмя;ТипПроверки;ИмяФормы;Заголовок, его можно править руками и хранить в репозитории.

Разбор результатов прогона
~~~~~~~~~~~~~~~~~~~~~~~~~~

Кнопка «Разобрать результаты прогона» читает каталог allure-results и делит падения
на две части:

  * штатные отказы конфигурации — «самостоятельное использование формы не предусмотрено»,
  «только на основании», «не выбран сегмент», «команда меню не найдена» — они дописываются
  в файлы исключений (объект и тип проверки берутся из тегов сценария);
  * всё остальное — выводится в лог как требующее разбора и в исключения не попадает:
  прятать настоящие ошибки исключениями нельзя.

Повторный разбор не дублирует уже имеющиеся строки.

Пакетный режим для CI/CD (FR-21)
--------------------------------

    1cv8 ENTERPRISE /F<база> /N<пользователь> /Execute АвтоТест1С.epf /CАвтоТест1С;<каталог>;<лимитОбъектов>;<лимитФорм> /DisableStartupDialogs /Out run.log

Лимиты необязательны: 0 — без ограничения, -1 для форм — не обходить интерфейс
(быстрый ночной прогон только серверных проверок). По завершении в каталоге появляются:

  * АвтоТест1С-<метка>.json — машиночитаемый результат для конвейера и трекеров задач;
  * АвтоТест1С-<метка>.html — отчёт для нетехнического заказчика (FR-19);
  * АвтоТест1С-<метка>.mxl — печатная форма с риск-картой и покрытием;
  * АвтоТест1С-старт.log / АвтоТест1С-финиш.log — отметки хода прогона для диагностики CI.
